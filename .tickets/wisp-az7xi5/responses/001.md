**Goal of this turn:** scout the wisp repository and the local environment, then present build options for a local wisp benchmark suite. No code was written.

**TLDR:** wisp already records tokens, price, time, and session structure; the repository has no benchmark runner or task corpus. Recommend a lightweight bespoke runner with small, large, compaction, and memory tracks, plus one Terminal-Bench task for external validity.

## What the scout found

**Metrics already exist.**

- Tokens: `<session>/wisp.usage` holds one JSON object per turn with `prompt_tokens`, `completion_tokens`, `cached_tokens`, `cache_write_tokens`, and `reasoning_tokens`.
- Price: `wisp.modelcfg` is copied at run start from `WISP_LLM_MODEL_INFO_FILE`. The local file `/home/pnagyux/.config/wisp/gratex-litellm-models.json` holds 31 models with input, output, cache-read, and cache-write prices per 1M tokens, plus context windows. The company endpoint does not reliably return a `cost` field, so the model table is the price source.
- Time: `wisp.log` carries epoch-ms on every event. `http_done ms=` is one turn's LLM latency; `tool end ms=` is one tool's latency. Wall-clock time must come from the runner.
- Pass/fail: wisp has no scorer. A benchmark task must ship hidden tests, and the runner must execute the tests after `wisp run`.
- Subagents: each child session has its own `wisp.usage`. The parent link in `wisp.run.json` and `wisp ls --tree` expose the tree. A team run must sum the whole tree.
- Turn cap: `WISP_LLM_MAX_TURNS` caps rounds. `wisp run --wallclock S` caps wall time; the default is 600 seconds.

**Compaction and memory are partly missing.**

- wisp has no in-run compaction. `wisp run --context-guard LIMIT` stops at a round boundary with exit 75 and keeps the session resumable.
- `wispy` implements compaction as a guard stop, a distill turn that writes `STATE.md`, and a new session that starts from the ticket plus `STATE.md`.
- wisp has no memory store beyond the transcript, project files, the AGENTS.md chain, skills, and wispy's `STATE.md`.

**Local assets are sufficient.**

- Company LiteLLM: the chat-completions endpoint named by `WISP_LLM_URL`. Models include `DeepSeek V4.1 Flash`, `GLM 5.3`, `Qwen 3.6 35B A3B`, `Qwen 3.8 27B`, and `GPT 6.1 Sol`. `wisp -t` sends `reasoning_effort`.
- Sandbox: Docker 29.5.2 and Podman (runc) work.
- Toolchains: Python 3, Node 24, Rust 1.95, Java 21, gcc, make, pytest. Go is absent.
- Prior local runner: `experiments/tool-status/harness.py` uses subprocesses, repetitions, JSONL results, and token/cost accounting.
- External benchmark: `~/code/curated-terminal-benchmark` has Harbor 0.24, a wisp agent arm over the GPT proxy, and 66 Terminal-Bench 4.0 tasks downloaded to `artifacts/datasets` (505 MB). The wisp arm accepts only `GPT 6.1 Sol` and needs a local-endpoint variant.
- Prior wisp results: tickets `wisp-3v9vog` and `wisp-3s5m3t` analyze 12 Terminal-Bench tasks against five harnesses.

## Options

| Option | Covers | Effort | Speed | Realism | Main risk |
|---|---|---|---|---|---|
| A. Bespoke light harness | small, large, compaction, memory | medium | fast | medium | task authoring |
| B. Terminal-Bench through Harbor | small, large | medium-high | slow | high | GPT plumbing, low local scores |
| C. Public small-task adapter | small only | low-medium | fast | medium | single-file tasks, saturation |
| D. Inspect AI | small, large | medium | medium | medium | integration, custom tasks still needed |

### A. Bespoke light harness (recommended)

Build `experiments/bench/` around a task contract: `task.toml`, `workspace/`, hidden `tests/`, and `solution/`. A Python runner copies the workspace to a temp directory, runs wisp with a profile, executes the hidden tests, and stores one JSON row per run. Small tasks run on the host; a task that needs isolation runs in Docker.

Four tracks:

1. **Small:** 40 mini-repos of 5-15 files. Families: 12 bugfix, 8 feature, 6 refactor, 6 data/CLI, 4 performance, 4 test-writing. Each task ships hidden tests and a reference patch. Calibration keeps tasks with a 20-80% pass rate.
2. **Large:** one multi-file service task with 30+ hidden tests, designed for 100+ tool calls. The single-run pass rate should start near zero.
3. **Compaction:** one long-context needle task, one guard-stop handoff task with three policies (no handoff, free summary, wispy `STATE.md`), and one fidelity quiz after compaction.
4. **Memory:** transcript recall within one session, cross-session state handoff, and standing-rule adherence from the system prompt or `AGENTS.md`.

Pros: fast, cheap, covers all four requested categories, full control of profiles, easy repetitions. Cons: task authoring and calibration are the main work; the mini-repos are synthetic.

### B. Terminal-Bench through Harbor

Extend the curated benchmark with a local-endpoint wisp agent. Harbor, the dataset, and the verifier plumbing already exist. Run six easy tasks for the small track and one hard task for the large track.

Pros: real tasks, hidden verifiers, container isolation, published baselines. Cons: the GPT proxy plumbing must be replaced; Docker or Podman is required; one trial takes 10-60 minutes; local models may score near zero; no compaction or memory coverage.

### C. Public small-task adapter

Port a subset of Aider polyglot (225 exercises, six languages, tests) or QuixBugs (40 tiny bug fixes) into the local runner.

Pros: real tests, little authoring. Cons: single-file tasks underuse wisp's tools; porting work; likely saturation; no large, compaction, or memory coverage.

### D. Inspect AI

Use Inspect AI (UK AISI) with wisp as a custom solver.

Pros: standard logs, scorers, parallelism, existing datasets. Cons: a new dependency; wisp's session model does not map cleanly; custom tasks are still needed; less control over per-turn accounting.

## Recommended shape

Take A for the small, compaction, and memory tracks. Add B for one large task as external validation. Defer C and D until the small suite saturates or the user wants a public comparison.

**Runner output.** One JSON row per task run:

```
{suite, task, profile, model, thinking, rep,
 pass, checks, duration_s, sessions, turns, tool_calls,
 tokens:{prompt, cached, net, output, reasoning},
 cost_usd, exit_code}
```

Aggregates: pass rate with a Wilson interval, median cost and time, cost per solved task, and paired per-task deltas against the baseline profile.

**Profile record.** One `profile` is `{model, thinking, persona_variant, topology, guard, memory_mode}`. The runner executes `profile x suite x repetitions`.

**Experiment matrix.**

- Baseline persona vs persona plus one coding guideline.
- Solo wisp vs wisp with the SUBAGENTS section and a delegation instruction.
- `-t low` vs `-t high` vs `-t xhigh`.
- Guard 32k vs 64k vs no guard, with and without wispy's `STATE.md`.
- No memory vs free-form notes vs structured state.

**Calibration.** Run 60 candidate small tasks on three models, one repetition each. Keep tasks with a pooled pass rate between 0.2 and 0.8. Freeze the kept set with a hash and record the model versions.

**Rough cost and time.**

- Small: 40 tasks x 3 repetitions x 4 profiles = 480 runs, about 45 seconds each, 8 parallel, roughly 45 minutes. DeepSeek cost stays under $5.
- Large: 6 runs x 10 minutes, roughly 1 hour.
- Compaction and memory: about 20 runs x 2 minutes, roughly 40 minutes.
