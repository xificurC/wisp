Goal: research `~/code/elephant-goldfish-model`, explain the methodology, and analyze a port to `wispy` or a new wisp workflow.

**One-sentence summary:** EGM is spec-driven development with a context-rich author and fresh-context adversarial reviewers; wisp supplies fresh contexts natively, so the review half ports cleanly and the drafting half needs one gate decision.

**Four-sentence summary:** EGM's one invariant is that the reviewer sees only the artifact, the rubric, and a reading list, never the drafting conversation. wisp gives that invariant directly through child sessions built with `wisp new -s persona`. wispy's ticket plus state replaces the Elephant's long conversation, but wispy distills and closes a session at every finished run, so EGM's approval gates need a decision. The rest of EGM is scaffolding for coverage: five review stages, seven brainstorm lenses, ten personas, and five rubrics.

## 1. What the repository holds

EGM ships 7 skills, 10 reviewer personas, and 5 rubric files. The corpus is 20,875 words.

| Part | Files | Size |
|---|---|---|
| Skills | `skills/*/SKILL.md` | 437–3,140 words each |
| Personas | `agents/*.md` | 196–916 words each |
| Rubrics | `resources/document_standards/*.md` | 182–373 words each |
| Guides | `docs/getting_started.md`, `docs/harnesses.md`, `docs/designs/architecture.md` | — |

`egm-review` alone is 3,140 words. `egm-bootstrap` is 2,933 words.

## 2. The method, in order

EGM calls the method Spec-Driven Development. Dave Rensin's essay is the source.

1. **Brainstorm.** The agent asks open questions, anchors a hypothesis, then spawns a seven-lens reviewer swarm. Output: `concepts_brief.md`.
2. **Draft.** The agent writes `design_draft.md` section by section. Each section ends at an approval gate. The agent then reconciles the draft against the brief and writes `docs/designs/FEATURE.md`.
3. **Review.** Five stages run in fresh contexts: Zoom Out, Comprehension, Critic, Intermediate Zoom Out, Implementation Readiness.
4. **Resolve.** The author classifies each finding as CONTEST, ESCALATE, PROPOSE FIX, or DECLINE. The author applies approved edits.
5. **Implement.** The design doc is the instruction. A weekly drift report compares docs against code.

The human owns every architectural trade-off. The agent never ranks options in `egm-draft`.

## 3. The mechanism

- **Skills** are slash commands. Each skill body is a long procedure: inputs, gates, subflows, exit conditions.
- **Personas** are subagent system prompts. Each persona is stateless and read-only by instruction.
- **Rubrics** are versioned files. A reviewer loads one rubric and audits one line range.
- **The synthesizer** is an intermediate subagent. The synthesizer fans out reviewers, dedupes findings, groups them by severity, and writes the report.
- **Artifact-first UX** bans long chat dumps. Every deliverable is a file.
- **Fresh context is mandatory.** EGM stops the review when the host cannot spawn a fresh subagent.

## 4. Why the method works

The reviewer cannot see the author's speculative hypotheses. The reviewer therefore cannot validate the author's faulty assumptions.

The rubric is fixed before the review starts. The author cannot move the bar mid-review.

The artifact is the only channel. Every finding cites a line in the artifact.

The human decides. The agent produces signal, not verdicts.

Those four rules are the method. The five stages, seven lenses, and eleven personas exist to raise recall and coverage.

A second useful property: the design doc is checked into the repo. Documentation drift becomes a diffable defect.

## 5. What wisp already provides

- `wisp new -s PERSONA` fixes the whole system prompt. A child inherits no conversation.
- `--parent` records lineage, and `wisp ls --tree` walks the tree.
- `wisp response -d CHILD` returns the child's final answer.
- `wisp.jsonl` records every round of every child. The record is the truth.
- `wisp skill read NAME` returns a skill body. `wispy --skills` puts named bodies into one persona.
- `wisp usage -d CHILD` prices each child separately.
- `wisp` sends only bash, python3, and load_image. Files are the UI.

## 6. The mapping

| EGM | wisp or wispy |
|---|---|
| `/egm-review file.md` | `wispy run --skills egm-review` |
| Subagent tool | `wisp new --parent -s persona`, `wisp run`, `wisp response` |
| Named persona | The persona file passed to `-s` |
| Goldfish isolation | A child session with no inherited turns |
| GoldfishContext | Paths in the child prompt; the child reads them |
| Document standard | A versioned file named by the skill body |
| Side-panel artifact | A file in the repo |
| Synthesizer | The parent aggregates child responses |
| `ask_question` gate | A chat turn between `wispy run` calls |
| FeatureRange versus DetailedRange | The skill splits the file at `## Detailed Implementation Plan` |

The mapping is close to one-to-one. wisp is a better host than EGM's own harnesses on two points. First, `wisp new -s` controls the entire system prompt, while Codex and Claude still inject repository instruction files. Second, each child picks its own model and thinking level, so the comprehension reviewer can run cheap and the design critic can run strong.

## 7. What fits cleanly

- **Fresh-context review.** The child prompt holds the document path, the rubric path, and the reading list. Nothing else crosses.
- **Parallel fan-out.** Start N children with `&` and `wait`, one `wisp.stream` each. Read each with `wisp response`.
- **Report files.** Reviewers write their findings to files. The parent reads only the deduped list, so the parent's context stays small.
- **Auditability.** EGM's reviews are opaque events. A wisp child's exact prompt, rubric, and findings sit in `wisp.jsonl`.
- **Cost control.** `wisp usage` prices each reviewer. A review stage becomes a measurable line item.
- **Rubrics as the stable interface.** The rubric survives a harness change. The skill is thin glue around the rubric.

## 8. Where the port breaks

1. **Gates.** `wispy` treats a finished work run as the end of the work. `drive()` saves the response, distills, and clears `.phase`. EGM assumes the model yields and the human replies in the same session. A wispy gate therefore either ends the session or needs a new marker.
2. **Elephant memory.** `egm-resolve` wants the session that wrote the document, because contesting a finding needs the earlier reasoning. A wispy distill discards that reasoning. The ticket must carry a Decisions section with rationale.
3. **Synthesizer nesting.** EGM puts a synthesizer between the author and the reviewers. wisp can nest, but each layer costs one model turn and one session. Direct dispatch is cheaper. The synthesizer earns its cost only when the parent's context is scarce.
4. **Prompt weight.** `egm-review` is 3,140 words. wispy pays the system prompt once per one-shot session. Porting all seven skills verbatim imports the complexity wisp exists to avoid.
5. **Read-only is instruction only.** EGM's Claude adapters set read-only tools. A wisp child always has bash and python3. A Goldfish can write unless the skill forbids it and the child works outside the repo.
6. **No question tool, no inline comments.** The shell is the UI. A gate is a run boundary plus a file the human edits.

## 9. Three port shapes

**A — Faithful plugin.** Port all seven skills, ten personas, and five rubrics. Behavior matches EGM closely. Cost: a 21k-word corpus to maintain, a 3k-word instruction file per review session, and one-failure-point fidelity to EGM's scaffolding.

**B — Thin goldfish layer plus a drafting pipeline.** Port the review half as standalone skills: `goldfish-review`, one skill per reviewer, and the rubrics as project files. Port `egm-draft` and `egm-resolve` as wispy skills. Skip `egm-bootstrap` and `egm-drift-report` at first.

**C — New workflow.** Use plain long-lived `wisp` sessions per artifact. wispy tracks the ticket only. A gate is `wisp run -d DIR <<< "approve"`. No distill loop, no gate problem, no ticket as the contract.

## 10. Recommendation

Take **B**, and keep **C** as the escape hatch for interactive drafting.

The review half is the part of EGM that pays for itself. Review maps one-to-one onto wisp, needs no wispy change, and matches the house style of `falsifier` and `checker`.

The draft half needs one wispy decision. The brainstorm swarm duplicates `brain`, `glasses`, and `pen`. The bootstrap skill duplicates `glasses`.

Concretely, build this first:

```text
.agents/skills/
  goldfish-review/SKILL.md        # fan out, dedupe, write report
  goldfish-zoom-out/SKILL.md      # personas as skills
  goldfish-comprehension/SKILL.md
  goldfish-design/SKILL.md
  goldfish-readiness/SKILL.md
docs/standards/
  feature-spec.md
  zoom-out.md
  implementation-readiness.md
```

The parent spawns one child per reviewer:

```sh
CHILD="$(wisp new --name "goldfish-$NAME-$TICKET" --parent "$SELF" \
  -m "$MODEL" -t "$THINKING" --env-in-system-prompt \
  -s <(wisp build-system-prompt --wisp --skills --agents-md \
       < <(wisp skill read "goldfish-$NAME")))"
printf 'Document: %s\nLines: %s\nRubric: %s\nContext: %s\n' \
  "$DOC" "$RANGE" "$RUBRIC" "$CONTEXT" \
  | wisp run -d "$CHILD" --context-guard 70% > "$CHILD/wisp.stream"
wisp response -d "$CHILD"
```

The parent writes `review_report.md` from the child responses. The parent dedupes and groups by severity. The parent never copies a full reviewer report into another prompt.

One improvement EGM cannot make: run two instances of each reviewer and diff the findings. The child sessions make the diff cheap.

## 11. The open decision

Which gate model does the drafting session use?

- **Run boundary.** No wispy change. Each gate ends the session and distills. The ticket carries the decisions. The cost is a context reset per gate.
- **Gate marker.** A small wispy patch. A marker file keeps `.phase` open and skips the distill. The session survives the human reply. The cost is one new state in wispy's model.
- **Plain `wisp` session.** No wispy loop. The session runs for the whole document. The ticket tracks the work. The cost is that wispy's distill discipline does not apply.

The review half needs no decision. The three shapes above change only the drafting half.
