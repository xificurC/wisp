Goal of this turn: show, as a pseudo-session, how pi survives an image read on a text-only model and recovers the image after a model switch, then map that onto a possible wisp port.

TLDR: In pi the image always lands in the stored record, every request downgrades it to a placeholder text when the model declares no image input, and a model switch later sends the stored bytes for real. A wisp port replaces the shipped tool-time refusal with this wire-time downgrade, but wisp cannot switch models mid-session, so the GLM 5.3 poison case needs a backstop.

## pi pseudo-session

Ground truth first, verified in the pi source at `~/code/pi` (commit 5f89cc0a7):

- The `read` tool always stores the image block in the tool-result record (`read.ts:284-295`). When the model declares no image input, pi adds a UI-only detail `imageUnsupportedByModel` (`read.ts:40-47`). The model never sees that detail.
- Every request passes through `downgradeUnsupportedImages` (`packages/ai/src/api/transform-messages.ts:60-101`). A model whose `input` array lacks `"image"` gets each image block replaced by one placeholder text: `"(image omitted: model does not support images)"` for user images, `"(tool image omitted: model does not support images)"` for tool-result images.
- A custom `models.json` entry defaults `input` to `["text"]` (`docs/models-configuration.md:38`), so an undeclared proxy model counts as text-only — the placeholder fires, and the request stays valid.

### Turn 1 — text-only model, image read

```
> /model custom-proxy-qwen        # models.json entry, no "input" declared → input: ["text"]

> What does chart.png show?
  [read tool] reads chart.png
    stored record (session history):
      content = [ text: "Read image file [image/png]"
                  image: <base64 bytes of chart.png> ]
      details = { imageUnsupportedByModel: "custom-proxy-qwen" }   # UI only

    wire request (this turn only):
      toolResult content = [ text: "Read image file [image/png]"
                             text: "(tool image omitted: model does not support images)" ]

  model replies: "I read chart.png but I cannot see images.
                 The file note says image/png. Describe it or check with bash."
  exit: normal. No HTTP error, ever.
```

The TUI prints `[custom-proxy-qwen does not support images; it saw a placeholder instead]` for the human (`tools/renderers/read.ts:118-120`).

### Turn 2 — second prompt in the same session

```
> Compare it with other.png
  [read tool] reads other.png → same shape: image stored, placeholder on the wire

    wire request now replays BOTH reads:
      toolResult #1: "Read image file [image/png]"
                     "(tool image omitted: model does not support images)"
      toolResult #2: "Read image file [image/png]"
                     "(tool image omitted: model does not support images)"

  model replies using the text notes. Run completes normally.
```

This is the property the ticket's poison chain lacks: the stored record never blocks a later request, because the downgrade is computed per request, not baked into the record.

### Turn 3 — model switch, image recovery

```
> /model GPT 4o-like-vision       # built-in entry, input: ["text", "image"]

> What color is the chart in chart.png?
    wire request replays the same stored history, unchanged on disk:
      toolResult #1: [ text: "Read image file [image/png]"
                       image: <base64 bytes — sent for real now> ]
      toolResult #2: [ text + image, also sent ]

  downgradeUnsupportedImages returns early: model.input includes "image".
  The model sees the actual pixels and answers about the color.
```

No repair step exists and none is needed: pi never rewrote the record, so the bytes were waiting. Pi explicitly reverted the alternative — storing a "model does not support images" note in the record — because that note went stale and replayed as false text after a model switch (CHANGELOG #12131).

## The port to wisp

What maps directly:

| pi mechanism | wisp counterpart |
|---|---|
| record always holds the image | `load_image` sets `record["attachments"]`; revert the shipped tool-time refusal so bytes are always stored |
| `downgradeUnsupportedImages` per request | one shared helper, called from `body_of_chat` (pending_images), `chat_image_message`, and the anthropic and responses builders; when `vision_enabled_of` is false, emit the placeholder text instead of the image part |
| UI-only capability note | wisp has no UI; the placeholder text itself tells the model and any log reader |
| custom model defaults to text-only | wisp keeps default-on `vision_enabled_of`, because wisp has no per-model catalog and default-off would disable every unconfigured vision model |

What the port changes in the shipped design (ticket items 3 and 4):

- The tool-time gate on `_run_load_image` goes away: `load_image` stores the image and returns exit 0, matching pi's `read`. The shipped gate's refusal text is a stored capability verdict; pi reverted exactly that shape because it goes stale and destroys bytes a vision-on run could send.
- The `--attach` start-time refusal is open decision (b): pi has no counterpart, since the wire downgrade covers user images too. Dropping the refusal and letting the placeholder speak is the consistent port.

What the port cannot copy:

- **Mid-session model switch.** pi recovers the image by `/model GPT 4o-like-vision` in the same session. wisp rebuilds each request from the stored records with the session's fixed model; a model change means a new session, and the new session loads its own `wisp.modelcfg`. The stored image survives on disk in wisp.jsonl, so a successor session on a vision model replays it — but nothing today launches that successor automatically. `wispy demote` is the nearest tool, and it starts a fresh session that would replay the image if the modelcfg allows.
- **The undeclared text-only model.** pi defaults custom models to text-only, so GLM 5.3-without-a-modelcfg-entry degrades to placeholders. wisp defaults vision on, so the same model still sends real image parts and still gets the HTTP 400. The port fixes the misconfigured case (modelcfg `vision: false`, `WISP_LLM_VISION=off`), not the unconfigured poison case. That case keeps needing one of: a modelcfg entry, the error-as-tool-response stop, or the `wispy demote` escape.

Open decisions (a) gate point, (b) `--attach`, and (c) the unconfigured poison case remain in the ticket `## Gaps`; the pseudo-session above supports (a) as the pi shape and (b) as dropping the refusal, but the call is yours.
