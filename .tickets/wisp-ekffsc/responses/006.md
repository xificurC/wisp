Goal: settle the wisp image-recovery design by reading how pi handles images for models without vision. I recorded the pi inspection in the ticket `## Gaps` and changed no code.

**TLDR:** pi never drops an image from history. pi replaces the image with a placeholder text in the request body, so the model reads the omission and the transcript keeps the bytes. wisp's shipped tool-time gate does the opposite, and it repeats a bug pi already reverted.

**Your first point is correct.** In wisp the request body is a pure function of the stored records. `body_of_chat` reloads every `attachments` field on every request, so the endpoint rejects the same turn forever. A new assistant reply never clears it.

**Your second point is exactly pi's position.** pi calls the aggressive option a lie too, and it fixed the problem with a placeholder, not a drop. The tool result keeps the text note and the image block. The request body sends `"(tool image omitted: model does not support images)"` in place of the image.

pi's layers, as read:

| Layer | pi's choice | Where |

| Declaration | `input: ["text","image"]` per model; a custom `models.json` entry defaults to `["text"]` | `providers/model-schema.ts:11,101`; `docs/models-configuration.md:38` |

The test name states the rule: `"should always read images (filtering happens at convertToLlm layer)"` (`test/block-images.test.ts:73`).

**The decisive fact for wisp.** pi stored the vision verdict in the `read` result once, and reverted that change. CHANGELOG #12131: the stored note "was replayed to the model as stale text after switching to a vision model". wisp's shipped `_run_load_image` gate writes the same kind of stored verdict. A record written under `WISP_LLM_VISION=off` then replays under `on` as a false refusal plus a missing image. The gate also throws away bytes that a later vision-on run could send.

**What pi does not do.** pi has no error-text sniffing, no retry without images, and no live capability query. The retry policy covers 408/409/429/5xx only (`utils/provider-retry.ts:30-36`), so a 400 reaches the user. pi escapes a bad 400 by switching models, and the switch works because history still holds the image. wisp cannot switch models mid-session, so wisp still needs `wispy demote` for a mis-declared model.

**Three deltas on the ticket's plan, for your decision:**

1. **Gate point.** Move the gate from tool time to the wire. `_run_load_image` always stores text plus image; a shared helper renders an image part or the placeholder note, and the three builders call the helper. This removes the stale verdict and keeps the agent honest: the agent reads "image not delivered" instead of a fake success or a silent drop.
2. **`--attach`.** pi does not refuse an attachment for a text-only model; pi downgrades it at the wire. The shipped `--attach` refusal has no counterpart in pi. Keep it for a cheap early warning, or drop it and let the placeholder speak.
3. **Poisoned histories.** If you pick the error-as-tool-response stop, copy pi's append-only `context_edit` (`targetId` plus `replacement` or `null`) instead of editing committed `wisp.jsonl` lines. The raw transcript stays readable and the model context is a projection.

**Defaults.** pi can default a custom model to text-only because the placeholder keeps every request valid. wisp has no per-model catalog, so text-only-by-default would disable vision for every unconfigured vision model. Keep wisp's default-on and accept one 400 per unconfigured text-only model, then `wispy demote`.

Your call needed on: gate point (wire only, or tool time plus wire), `--attach` (keep or drop), and the mis-declared-model recovery (demote alone, or the error-as-tool-response stop with `context_edit`).
