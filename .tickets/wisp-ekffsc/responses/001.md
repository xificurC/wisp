Goal: plan the resurrection path for a wispy flow stuck on `load_image`, and the fix that keeps `load_image` from poisoning a session on a text-only model. The plan is settled in the ticket; no code changed this turn.

**TLDR:** `load_image` succeeds locally, stores image bytes into the committed tool record, and every later request replays them as `image_url` parts; GLM 5.3 answers HTTP 400, wisp exits 77, and wispy retries a distill on the same poisoned session forever. Fix: a per-model vision gate that degrades `load_image` to a text result, plus a `wisp strip-images` repair command.

**The stuck chain (confirmed in code):**

1. `Tools._run_load_image` (wisp/wisp line 3621) reads the image into `record["attachments"]`; the round commits to wisp.jsonl with the bytes inside.
2. The next request replays the record: `body_of_chat` (line 4441) and `chat_image_message` (line 4466) send the attachments as `image_url` data URIs (responses and anthropic builders do the same).
3. GLM 5.3 via the company LiteLLM server answers 400; the run exits 77 (`kind=http`).
4. wispy `decide_after_work` (wispy/wispy line 433) maps rc 77 with finished work to a distill in the same session; the distill replays the same attachments, fails with the same 400, and `.phase` stays `distill`. Every `wispy continue` retries that distill on the same session — the loop never escapes.

**The plan (ticket wisp-ekffsc, all tasks open):**

1. `wisp strip-images -d DIR` — resurrection. Rewrites wisp.jsonl under the run lock, dropping `attachments` from tool and user records and appending a note line. After the strip, `wispy continue` unsticks the flow.
2. `wisp.modelcfg` gains a `vision` boolean per model (filled from `WISP_LLM_MODEL_INFO_FILE`).
3. `_run_load_image` checks `vision_enabled_of` (env `WISP_LLM_VISION` > modelcfg `vision` > default on). Vision off degrades to an exit-1 text result telling the model to inspect the file with bash/python3 — no `attachments` field is ever set, so the conversation never carries image parts. The gate sits at tool time, covering all three providers at once.
4. `wisp run --attach` fails at start under vision off, before the prompt is read.
5. wispy maps wisp rc 77 to the `api` action (keep work, repair note) instead of starting a distill that replays the same endpoint error.
6. Tests for the gate, modelcfg parsing, strip-images, the attach refusal, and the wispy mapping.

**Out of scope (recorded in the ticket):** mid-run auto-strip on a 400 (self-healing retry), OCR or image description, and changes to the providers' image wire formats.

**One decision for you:** the default when a model has no `vision` entry in modelcfg is *allow* (current behavior), so unconfigured text-only models can still poison a session until the model table carries `vision: false`. The alternative, default deny, breaks vision models that lack config. The plan keeps default allow; say the word if you want deny.
