## Why a new prompt does not work today

A request body is a pure function of the stored records. Every run calls `load_events`, which reloads all of `wisp.jsonl`, then appends the new prompt and calls `build_request`. All three provider builders — `body_of_chat` (pending_images, line 4519), `items_of_anthropic`, and the responses builder — convert every record with an `attachments` field into image parts. So the new prompt text is new, but the replayed history still carries the image bytes. The 400 kills the request before the model reads the new prompt. The loop repeats identically forever. Nothing between runs inspects or changes the stored image.

## The design, restated precisely

On an HTTP 4xx from a request whose loaded records hold attachments: rewrite those records — drop `attachments`, set the tool content to the delivery failure with the raw server text and the file path, set exit nonzero — persist, stop the run. The next run or `wisp continue` replays a text-only conversation; the model reads the degraded tool response and adapts.

## Why it is the right layer

- It fixes the stored record, the one representation all three builders share. One choke point covers every provider, same argument as the tool-time vision gate.
- No cross-run state. Strip-retry needed a learned `vision_learned_off` flag and hit the `refresh_model_cfg` overwrite problem. Here the sanitized conversation itself is the state.
- No masked failures. A wrong-format 400 on a vision model is not remembered as "vision off"; each failure is recorded per call, factually, and the model can re-call `load_image` — the source file stays on disk.
- The stop already exists. `main` catches `HttpError`, exits 77, and the ticket's rc 77 → wispy `api` mapping already tells the user to retry. The rewrite is the only new code; the retry it asks for then succeeds.

## Issues found — real, all manageable

1. **The rewrite targets committed lines.** The attachment record commits at the round boundary (`loop_rounds` flushes right after `tools.execute`), before the next turn raises. `flush_records` appends only records past the commit point, so mutating the in-memory record persists nothing. The rewrite must rewrite `wisp.jsonl` itself. Precedent exists: `_reload_committed` already rewrites the log when dropping a partial tail. The new path must run inside `commit_guard` and log one degraded line per record.
2. **Trigger condition.** Recommended: status 400–499 while any loaded record holds attachments. No error-text sniffing. Misattribution is one-shot and honest: if the 400 had another cause, the rewritten text quotes the raw server message, the next request holds no images so the trigger cannot fire again, and plain rc 77 plus the wispy api/demote backstop still apply.
3. **`--attach` must be in scope.** `wisp run --attach` puts attachments on the user record (line 1177). With vision unconfigured, the first request 400s and the rewrite target is a user record. Strip only the `attachments` key and append a delivery note to the record text; the prompt text stays untouched. Without this, one poison path stays open.
4. **Exit code.** Keep 77, extend the error line ("N image records degraded; wisp continue to proceed"). Exit 0 would send wispy straight into a distill of a turn that produced no assistant reply.
5. **Cost.** The model reacts on the next run, not inside the failing one — one extra run lifecycle per failure. An unconfigured text-only model pays one 400 per image-bearing run; the modelcfg `vision: false` entry removes that cost for known models.

## Recommendation

Adopt this design as the recovery layer. Keep `vision: false` in modelcfg as the long-term static layer. Keep `wispy demote` as the generic backstop. Drop strip-retry and the `/model/info` query. The Out of Scope line "a mid-run auto-strip can come later" needs amending, since this design strips without retrying.

Open decisions before implementation: trigger statuses (400 only vs any 4xx), rc 77 vs 0, user-record rewrite for `--attach`, and new ticket vs a unit in this ticket. The full evaluation sits in the ticket's Gaps section.
