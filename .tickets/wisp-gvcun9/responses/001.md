**Goal: determine whether `wisp render-live` can stream tool calls and tool outputs instead of rendering them in one batch.** Findings are recorded in `.tickets/wisp-gvcun9/ticket.md`.

**TLDR: Both can stream. Tool-call streaming is a small change because the argument deltas already travel on the stream; tool-output streaming is medium and needs two design decisions first.**

## Current behavior (verified in code and a synthetic run)

The live pipeline is already incremental at line granularity: `sse_stream` (wisp:4136) writes each raw SSE line to stdout with flush as it arrives, and `render_records` renders each stdin line on arrival. Thinking and answer text stream live today. The batching is specific to tools:

- **Tool calls batch for two stacked reasons.** First, the producer: `wisp run` injects one complete `{"wisp":"tool_call"}` line only after the entire model turn ends, inside `Tools._execute_one` (wisp:2832). Second, the consumer: the model streams the command as tool-call argument deltas (`delta.tool_calls[].function.arguments` fragments) that already reach `wisp.stream` as raw SSE lines, but `Renderer.chunk` (wisp:4549) renders only reasoning and content fields and drops them. A synthetic run confirmed: delta lines produced no output; only the inject line rendered the `[bash 5s 5kb]` header plus fenced command.
- **Tool outputs batch at emission only.** `Executor.run` (wisp:2509) already reads subprocess output incrementally (select loop, 64kB reads) but routes it into memory or spill and returns it at process exit; `_execute_one` then injects one complete `tool_result` payload (wisp:2859). The data passes through wisp live; only the injection waits.

## Tool-call streaming: yes, small

Two designs:

1. **Renderer-only.** Teach `Renderer.chunk` to render tool_calls deltas. Drawback: the raw stream carries three provider dialects (openai-chat, openai-responses events, anthropic content_block events), so the renderer needs three parsers plus buffered JSON-unescape handling, because an escaped `\"` can split across two deltas.
2. **Producer inject, recommended.** `sse_stream` holds the provider-normalized chunk (from `chunk_of`, wisp:3927+) before yielding; it can inject `{"wisp":"tool_delta","index":...,"arguments_delta":...}` per delta. One dialect, provider-independent. Display opens the `[bash ...]` header when the name delta arrives, streams the command text, and closes the fence at turn end. `records_to_stream` (wisp:4609) can synthesize the same deltas from stored records for render-past parity, the way it already synthesizes content deltas. Non-stream mode (`WISP_LLM_STREAM=false`) degrades to batch, matching its nature.

Value: the human watches the command form and can Ctrl-C before it runs. Effort: about 30-60 lines plus tests.

## Tool-output streaming: yes, medium, two decisions first

Mechanics: give `Executor.run` a callback that injects `{"wisp":"tool_output","call_id":...,"content_delta":...}` per read chunk, then the terminal `tool_result`. The model-facing contract stays untouched — the stored record and the model message keep the final complete content, so replay and the byte-stable cache body do not change.

The two decisions:

1. **Status placement.** `Renderer.tool_result` prints `wisp:tool bash exit=N ms=M` before the content — the prefix placement settled in `md/design/tool-result-status.md`. Exit code and duration exist only after process exit. Streaming needs either a provisional "running" header plus a final status line, or text first and status after, which contradicts the settled placement.
2. **Cap policy.** The stated render-live invariant is "the same text the model receives". A live stream can show everything (the point of watching a long build) or respect maxKilobytes; the first breaks that invariant, the second caps the watch.

Also needed: `call_id` on every delta for attribution, a trailing SGR reset after the last delta (pinned by `test_wisp_tool_status.py`), timeout/drain partial output that streams then closes, and tolerance in old renderers — the current `render_line` skips unknown markers, so the change is additive and backward compatible. render-past stays batch, which fits its role as the settled view. Effort: about 100-150 lines plus tests.
