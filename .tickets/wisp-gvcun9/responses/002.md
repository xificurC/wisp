**Goal:** answer whether pi needs a translation layer like the injected `wisp:` markers, or whether pi parses the SSE stream directly, and compare both routes for wisp.

**TLDR:** pi never parses provider SSE outside its LLM client library. That library normalizes every provider stream into one typed event, and pi's out-of-process JSON mode forwards those normalized events as JSONL — which is the injected-marker design wisp's Option B proposes.

## pi does have the layer — in the library, not the renderer

`packages/ai` maps every provider stream into one `AssistantMessageEvent` (`packages/ai/src/types.ts:831-841`) with `toolcall_start`, `toolcall_delta`, `toolcall_end`. Ten adapters pay the dialect cost once each: `api/openai-completions.ts:450`, `api/anthropic-messages.ts:1046`, `api/openai-responses-shared.ts:530`, `api/google-generative-ai.ts:213`, `api/bedrock-converse-stream.ts:681`, `api/mistral-conversations.ts:730`, `api/pi-messages.ts:273`. No display code reads a provider payload.

So pi does not "use the SSE stream directly" anywhere except inside those adapters. The translation layer is mandatory for a multi-provider agent. The only question is where the layer sits.

## How pi then feeds a display

- In process: `agent-loop.ts:440` forwards the typed events as `message_update`. `modes/interactive/interactive-mode.ts:3654` creates a `ToolExecutionComponent` on the first `message_update` that carries a `toolCall` block, and calls `updateArgs()` on every later one. The command therefore draws while the model writes the command.
- Partial arguments reach that component as a parsed object, not a text fragment: `durable/src/harness/partial-changes.ts:64` feeds `StreamingJsonParser` with each `toolcall_delta`. pi pays the split-fragment cost once, in the parser.
- Tool output streams through an `onUpdate` callback (`core/tools/bash.ts:293`), throttled at 100 ms (`core/tools/renderers/bash.ts:19`), carrying a snapshot bounded to 2000 lines / 50 KB (`core/tools/truncate.ts`) plus the path of the full output in a temp file.
- Out of process: `--mode json` and `--mode rpc` emit JSONL derived from the same typed events. `modes/json-event.ts` strips the cumulative snapshots and keeps the deltas. `docs/json.md` documents `toolcall_delta {contentIndex, delta}` and `tool_execution_update {toolCallId, partialResult}`.

That last bullet is the key one: when pi's display sat outside the producer process, pi emitted normalized per-delta records. pi did not emit provider SSE for the client to re-parse.

## Direct SSE vs injected normalized records

| Dimension | Direct SSE (wisp Option A) | Injected normalized records (wisp Option B) |
|---|---|---|
| Who normalizes | Every display, again | The producer, where `chunk_of` (wisp/wisp:4091) already normalizes |
| Implementations | Two: producer and renderer | One |
| Dialects the renderer knows | Three today, plus one per new provider | Zero |
| Split JSON fragments | Renderer must buffer and unescape `\"`-split argument text | Renderer appends one string field |
| Provider identification | The stream names no provider; `sse_stream` writes only provider lines and `wisp:` lines, so the renderer must sniff event shape | The producer knows the provider by name |
| Wire cost | Zero extra bytes | One added line per delta |
| render-past parity | Renderer parses stored raw lines; wisp does not store raw lines | `records_to_stream` synthesizes the same marker from the stored arguments string |
| Backward compatibility | No stream change | Additive marker; `render_line` falls through silently on unknown `wisp:` markers |
| Third-party consumers | Each re-implements the normalization | Read one documented shape |
| Failure mode | A dialect change breaks the display | A dialect change breaks the producer only, where tests already live |

## What the comparison shows

pi's JSON protocol and wisp's Option B are the same design. The reason is not taste: a display outside the producer process can only read serialized records, and serialized provider SSE puts the normalization burden on every reader.

wisp has one extra argument for Option B that pi's design also implies. wisp already owns the normalized chunk at the inject point; `chunk_of` sits inside `sse_stream` three lines above the `yield`. Option A pays a second implementation of that normalization inside the renderer, and the renderer cannot even tell which provider dialect it reads.

## Where pi's precedent does not transfer

- Status placement. pi re-renders a whole TUI block, so pi appends elapsed time at the end and never needs a provisional prefix. wisp's render-live writes append-only lines, so wisp must choose between a provisional `running` header and text-before-status. pi's precedent says nothing here; `md/design/tool-result-status.md` still governs.
- Cap policy. pi resolves the cap question by precedent: live view and model view are both the bounded window, and a temp-file path points at the full text. The durable harness adds `droppedBytes`/`droppedLines` on the live slot (`packages/durable/src/harness/live.ts:24-40`). That favors wisp's "respect `maxKilobytes`, point to the rest" over "stream everything".
- Snapshot vs delta for tool output. pi's JSON mode sends `partialResult` as a cumulative snapshot, because a screen-owning client can replace the block. An append-only line renderer cannot replace, so wisp needs content deltas plus dropped counters.
