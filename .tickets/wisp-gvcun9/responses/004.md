## TLDR

I merged the two trailing metadata lines per tool call into one `wisp:tool` line that carries the call's limits and the outcome. I verified both streaming claims: the command does grow while the model writes it, and `echo hi; sleep 60; echo bye` prints `hi` immediately — with one caveat about programs that buffer their own stdout.

## Goal

The goal of this turn was to remove the duplicate tool metadata and to confirm the two streaming behaviours the change implies.

## What changed

One `wisp:tool` line now closes each tool block. `[bash 30s 50kb]` is gone.

Before:

```
```
echo "hi" there
```
[bash 30s 50kb]

hi there
wisp:tool bash exit=0 ms=5
```

After:

```
```
echo "hi" there
```

hi there
wisp:tool bash timeoutSeconds=30 maxKilobytes=50 exit=0 ms=5
```

Mechanics:

- `Renderer.tool_header` writes only the fence and parks `timeoutSeconds` and `maxKilobytes` in `Renderer._budget`.
- `Renderer.tool_result` passes that pair to `tool_text_of(rec, budget=())`, which inserts the two tokens between the name and `exit=`.
- The model wire does not move: `tool_text_of(rec)` with no budget still derives the prefix header from the record alone. The record never stored the requested limits, so the human line keeps exactly the two facts the old tag line already carried for the human only.
- A bare `tool_result` with no preceding header prints the old line, with no budget.
- A `load_image` call with a bad path draws no fence and no tag; the status line alone names it.
- `timeout_s=` keeps its meaning: the timeout that fired. `timeoutSeconds=` is the limit the call asked for. On a timeout both carry the same number.

Accepted tradeoff: while a command runs, no status line describes it until the process exits.

## Verification 1: the command streams

Yes. `sse_stream` injects one `{"wisp":"tool_delta",...,"arguments_delta":...}` marker per provider-normalized argument fragment, and `Renderer.tool_delta` appends only the newly decoded text. Measured with four fragments written 0.5 s apart, the renderer wrote at t=0.0, 0.5, 1.0, 1.5 s:

```
0.0 '```\n'
0.5 'git '
1.0 "log --oneline -n 50 --format='%h %s"
1.5 " %an' --since='30 days ago'"
```

The decoded field is `command` for bash and python3, `path` for load_image, raw arguments otherwise. The display starts when the `command` key token closes in the partial JSON, so a long command streams even when earlier keys (`timeoutSeconds`, `maxKilobytes`) precede it.

## Verification 2: the output streams

Yes, through `Executor.run`'s `on_head` seam, one `tool_output` marker per read chunk. Measured through wisp's own `Tools` and `Executor` with `echo hi; sleep 3; echo bye`:

```
0.00 content_delta: "hi\n"
3.01 content_delta: "bye\n"
3.01 tool_result
```

Caveat: this works because bash's `echo` builtin writes with a raw syscall. A program that uses stdio buffering prints nothing into the pipe until its buffer fills or the process exits. Measured through the same executor: `python3 -c 'print("hi"); time.sleep(3); print("bye")'` delivered both lines at 3.16 s, in one chunk. `cat`, `grep`, and most C programs behave the same way.

To make a long build stream, unbuffer it in the command the model writes: `PYTHONUNBUFFERED=1 python3 ...`, `stdbuf -oL -eL make`, or `grep --line-buffered`. Bash builtins and `echo` need nothing.

## Containment

- The stream carries only the bytes that enter the model-facing head, so the watch respects `maxKilobytes` and the spill tail never streams.
- `render-past` and `render-live` stay byte-identical: `records_to_stream` emits the stored `tool_call`, which parks the same budget, then the stored result, which closes with the merged line. A `diff -u` on a `tests/fixtures/fake_llm_sse.py tworound` run differs only in the `[user]` block that render-past adds.
- Two shell tests pinned the old tag line; their render-past grep now looks for `wisp:tool bash `.
