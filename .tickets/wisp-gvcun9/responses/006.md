**Goal:** test whether `wisp render-live` stalls mid-tool-call and then dumps the rest in one chunk.

**TLDR:** The stall is real, and the company LiteLLM endpoint causes it, not wisp. The endpoint sends the tool-call arguments of `deepseek-v4.1-flash` in a few coarse fragments, and wisp forwards each fragment the instant it arrives.

**Method.** Two measurements, both in `/home/pnagyux/code/wisp/wisp-sessions/wisp-gvcun9-006/probe/`.

- `provider_timeline.py` POSTs a streaming chat body straight to `$WISP_LLM_URL` with urllib and timestamps every `data:` line as urllib reads the line off the socket. wisp sits outside this path.
- A second run pipes `wisp run` into `wisp render-live` and byte-stamps the renderer's stdout with `stamp_bytes.py`.

**Reproduction.** The prompt asked for one bash call whose command writes a 6.5 kB heredoc. Raw socket timeline, `deepseek-v4.1-flash`, no thinking:

```
 17.669 + 0.045 tool_call name=bash args=''
 17.699 + 0.030 tool_call args='{"command": "'
 17.712 + 0.013 tool_call args="cat <<'EOF' > /tmp"
 22.735 + 5.023 tool_call args="/wisp-probe-big.txt\nline 01: ..."   # 6.6 kB
 22.750 + 0.015 tool_call args='"}'
```

Five argument fragments, a 5.0 s silence, then the whole 6.6 kB body in one fragment. `reasoning_effort=xhigh` gave the same shape with a 6.7 s gap, and dropping `stream_options.include_usage` changed nothing. A nonce in the prompt was needed, because LiteLLM's response cache otherwise replays a finished turn as one chunk.

**wisp adds no delay.** The 790-byte version through the real binaries: the renderer wrote `` ```bash `` at 0.840 s and `cat <<'EOF' > /tmp` at 0.900 s, then the rest at 2.169 s. The raw `wisp run` stream carried those two fragments at 1.015 s and 2.269 s. Render latency is milliseconds, and the 1.27 s hole matches the provider hole.

**Granularity is model-specific.** Same endpoint, same prompt, other local models:

| model | argument fragments | longest gap | longest fragment |
| --- | --- | --- | --- |
| deepseek-v4.1-flash | 5 | 5.02 s | 6.6 kB |
| glm-5.3-flash | 1633 | 0.19 s | 20 B |
| qwen3.8-27b | 455 | 1.31 s (one pause) | 20 B |
| mimo-2.6-flash | 1720 | 0.07 s | 20 B |
| laguna-s-2.1 | 1812 | 0.07 s | 20 B |

`deepseek-v4.1-flash` streams its reasoning at about 15 ms per fragment (1122 fragments in one run) and its answer text in small fragments. The buffering sits on that model's tool-call argument path only, at the endpoint side.

**What the eye sees.** The endpoint's early fragment is `{"command": "`, which decodes to empty text. The drawn prefix is the tail of that early fragment, such as `cat <<'EOF' > /tmp`. The renderer then holds the open fence until the next fragment lands, which is the freeze the user saw.

**Action taken.** No code change; the pipeline is byte-incremental end to end, and only the endpoint can send finer fragments. A short "Fourth pass" section in `.tickets/wisp-gvcun9/ticket.md` records the measurements. The only wisp-side lever is cosmetic: a placeholder or spinner during the wait, if the user wants one.
