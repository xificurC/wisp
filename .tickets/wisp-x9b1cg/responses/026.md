## 1. `agent-type:reviewer.approved<4` counts atoms

Yes: `--cap EXPR<N` counts the atoms that match `EXPR` space-wide and blocks the firing at `N`. `parse_cap` splits the trailing `<4` off, and `count_cap` counts every `agent-type:reviewer.approved` atom. The atom's value (a bool) is not compared, so the count is the number of reviews, no-go included.

The reading hazard is real and the spelling causes it. Recommendation: `--cap 'count(agent-type:reviewer.approved)<4'`, a required `count(...)` wrapper that marks the aggregate; a value test still goes inside the count. Recorded as N23.

`ran` is rejected. A counter atom is a derived fact with a writer: it drifts when a counter write is lost, and it counts starts rather than finished runs. A count over terminal atoms is arithmetic over the log and cannot drift.

## 1b. The same string in `--event` is worse than ambiguous

A probe of `conjunct_matches` shows `agent-type:reviewer.approved<4` matches both `approved=true` and `approved=false`, because a bool atom is coerced to int (`int(True)=1<4`, `int(False)=0<4`). `agent-type:worker.failed<4` never matches the string reason. The fix: type-strict matching, plus an `add_rule` refusal where the declared field type is known.

## 2. `--in task:prompt` on `continue`

As written, the repeat was necessary: §4.14 said a rule-level `--in` **replaces** the agent's inputs, so dropping `task:prompt` would drop the task. That text was wrong, and its own example (`--run agent:pickup --in session-file:handoff.md`) already assumed inheritance.

The owner's reading is now the design: a rule's `--in` **extends** the agent's list. Agent entries come first, an exact repeat is dropped, and the merged list lands on the run row. The recipes become:

```
ember rule add --id loop --event 'agent-type:reviewer.approved=false' \
  --run agent:pickup --in .out \
  --cap 'count(agent-type:reviewer.approved)<4'

ember rule add --id continue --event 'agent-type:worker.handoff=true' \
  --run agent:pickup --in session-file:handoff.md
```

One related source fact: a `cells` row records the writing run, but `briefing_of` resolves `.out` through `latest_cell`. The design says `.out` is the triggering run's output version. Run-scoped resolution is a one-line fix, and a failed trigger then prints `(no output version yet)` instead of a stale path.
