**The goal of this turn:** answer five objections to the ember design, and rewrite the design and the ticket around the answers.

**One sentence.** The warden is a mail clerk that labels mail rather than a dispatcher that holds the queue; big handoffs move as files or stdin and arrive as pointers; addressing is space-scoped with bare names and two verbs; the tail is a branch and never a decision, which closes the delivery race; and the rate limiter binds on the account, not the model.

**Four sentences.** A warden reads the digest and writes a typed proposal row, and the hearth executes only an op that the hearth already implements as arithmetic, with policy per op defaulting to advisory. Message bodies ride the steer inbox, the digest carries a bounded excerpt, and a body over 2 KB arrives as a pointer, so a 200 KB handoff costs the reader one tool call and costs nothing when unread. Addressing drops the `@` sigil: `ember send` broadcasts inside the sender's space, `ember dm alice,bob,role:rev` resolves a set, `all` stays a legal member name, and no syntax reaches another space. The final-answer case and the steer-inbox rename race are both real, and both close by treating a refused `continue` as a branch plus a marker-based redelivery; rate limiting now has two buckets, and the account bucket binds.

## 1. The warden, and what the warden is for

The hearth decides everything by arithmetic: who is a member, who holds a slot, who gets the next wake. Four decisions have no rule that expresses the decision. Each of the four becomes one typed row:

- `coalesce` — three messages are one question.
- `expect_reply` — one message is a question, not a report.
- `spawn` — one piece of work wants a new member, and one template fits.
- `escalate` — one thread belongs to the owner, not to the ember.

The warden writes one of those rows. The hearth executes only an op that the hearth already implements as a mechanism, with policy per op, default `advisory`. An unknown op, a malformed row, or an id already consumed becomes `warden.rejected` plus one advisory line.

Minimal example. Ember `lab` holds `w1 lead`, `w2 rev`, and `wz warden`. The owner asks `w1` to merge the lexer fix. In sixty seconds `w1` receives four messages from two senders: "red on test_lex_88", "why?", "off-by-one at lexer.py:88, fixing", "status?". That is six wakes for one question. Hash dedupe merges nothing, because the wording differs, one message is a reply, and one sender is the owner. `wz` wakes on a queue-depth trigger, reads the digest excerpts, and writes:

```
warden.proposed {op: "coalesce", ids: ["12a1","12a3","12a4"],
                 as: "lexer fix: red at 88, off-by-one, w2 fixing"}
```

Under `auto`, the hearth merges the three ids, and `w1` pays one turn instead of three. Under `advisory`, the owner sees one line and two verbs: `ember take 12a1`, `ember drop 12a1`. Each body stays readable with `ember show`.

Zero latency holds in all three failure modes. A warden that never wakes changes nothing. A warden run that hangs changes nothing. A warden that writes garbage produces one rejection row. The accounting rule: a warden wake costs one turn, so the warden fires only when the expected saving is at least two turns. The trigger is queue depth, never a timer.

## 2. Big messages: file or pipe, never argv

For me, a body that already exists as a file is cheapest: `ember send --now -F spec.md` puts the body in my prompt once and in the receiver's context once. A heredoc through stdin is equivalent when the body exists only in my head. An argv string is the form to avoid, for three reasons: Linux caps one argv string at 128 KiB regardless of the 4 MiB total (verified: 130 KB passes, 200 KB dies with `E2BIG`), quoting is a hazard, and `<<<` silently adds a trailing newline.

The CLI therefore takes four body sources: stdin, a heredoc, `-F FILE` (with `-F -` for stdin), and an argv string under 4 KB only.

The store keeps one content-addressed body row per distinct text, so a broadcast to ten members stores one copy. The wire form follows size: ≤ 2 KB inline in the steer line, > 2 KB a pointer, `body: ember show 12a1 (14 KB, sha256 ab12…)`. `ember show --head 80` and `--range 120:200` exist because the reader's tool cap is 5 kB by default. `msg.read` records the range.

## 3. Namespacing and the `@` sigil

The `@` sigil is gone, and `all` is a legal member name.

```
ember send --now "..."                 # broadcast inside my space
ember dm alice,bob,role:rev --now "..."  # a resolved set
```

A name matches `[a-z0-9][a-z0-9_-]*`. A colon is reserved, so `role:rev`, `id:w-7c1e`, and `state:live` never collide with a name. `send` with no recipient is the only spelling of a broadcast, so no target word needs reserving. `ember dm all` reaches the member named `all`.

Space scope: a send resolves only inside the sender's space, and the hearth checks the sender's space on every delivery row. No syntax reaches another space. A member that joins two spaces is the one legal carrier across the two spaces, and both spaces' logs show the two rows. That is an audited act by a named member, not a routing feature.

## 4. The final-answer case and the TOCTOU set

The delivery rule is now inbox-first. Message bodies ride `wisp.steer.inbox`; the digest is a bounded prompt with roster, ids, and a 120-character excerpt. Both `wisp run` and `wisp continue` drain the inbox before building a request, so the tail only chooses how a run starts, and a wrong guess costs a retry, never a message.

The final-answer case, verified end to end: after a stop-finish assistant tail, `continue` exits 1, the inbox survives, and `wisp run` with the digest prompt delivers the message as a steered record before the prompt. The hearth re-checks the marker at `run.ended`, so a soft wake is a promise with a deadline and not a hope.

The race you suspected is worse than suspected, and it is in wisp, not in ember. `wisp steer` opens the inbox and then writes; `steer_intake` renames the inbox away, reads the file, and removes the file. A write that lands after the removal goes into an inode with no name. Reproduced with no model: reader saw `''`, inbox gone, message lost. Ember heals the loss rather than pretending to prevent the loss: no marker means no cursor advance, and the message is redelivered. The inbox is a courier, never the record.

The full race table is design §S11, seven windows with the mechanism that closes each one.

## 5. Rate limits, and the cap

Corrected: the account bucket binds first, the model bucket second. Every `usage` row lands in both buckets. The account bucket is a budget, not a claim on the provider limit, because ember cannot see the interactive sessions and other agents that spend the same user quota. Default `EMBER_ACCOUNT_BUDGET = 0.5 ×` the provider limit. A 429 with a model scope parks the model; a 429 with an account scope, or with no scope, halves the account bucket and parks the account. The concurrency cap is 3, as you said.

## 6. Note versus wake

Both write the message into the member's inbox. Only a wake starts a run. A note is free and can wait for hours, and the note rides the member's next natural wake. A wake costs one turn now. That is the entire difference, and the default stays open as Q3.

## 7. How a spawn happens

`ember spawn --template reviewer --name rev --job "audit lexer.py:88"` writes `spawn.requested`; the hearth validates template, depth, count, and budget; the hearth calls `wisp new --name rev --parent <requester session> -m <routed> -s <persona>`; the hearth registers the member `idle` and runs nothing. A spawn costs one directory and zero tokens. `--send "..."` adds the first message in the same transaction, so spawn plus task is one wake and one turn. A fresh member is not woken at once; `--probe` is the opt-in smoke test for a new template.
