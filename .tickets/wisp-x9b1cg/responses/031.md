**Goal of this turn:** answer what a single SQLite DB for all spaces costs, recommend a store shape, and record the decision question in the ticket. No code was written.

**TLDR:** One DB for all spaces costs three things — space portability, physics-grade cross-space isolation, and corruption isolation — and buys exact global admission plus one-query observability. The recommendation is one DB with the losses mitigated, recorded as question N28, coupled to N27.

**What one DB loses**

1. **The self-contained space.** Today a space is one directory holding `ember.db`, `runs/`, `work/`, `agent-types/`, `cells/`, and `logs/`; the directory's existence is the registry, and copy, archive, delete, and inspect are file operations. With one DB, the registry becomes a `spaces` table holding each space's path. Deleting a space directory leaves orphan rows; moving it breaks the path-to-rows pairing. Portability then needs an `ember space export` verb.

2. **Isolation as physics.** Round 7 forbids rules, atoms, cells, trees, and steers crossing spaces. Per-space files enforce that with file boundaries: no query can reach another space. One DB moves the invariant into every query: each table (`atoms`, `rules`, `runs`, `consumed`, `joins`, `cells`, `files`) and each fixed `meta` key (`settled`, `report:<rid>`, `closure:<root>`) needs a space binding, and one missing filter is a cross-space leak. Verified in source: `atoms.seq` is a per-file `AUTOINCREMENT`, `settled` is a fixed meta key, and cell names are user-chosen, so all three collide or globalize in one file.

3. **Corruption blast radius.** One corrupted file takes every space's history. Per-space files isolate per space.

**What one DB buys**

- Listing spaces and cross-space metrics are single queries with joins; one backup file; one debugging session.
- The global cap becomes exact by construction: `live_runs` over one file, replacing the cross-store count and round-robin that N27 (a) otherwise needs.
- The one-writer law simplifies: the hearth loop is single-threaded (verified in `serve`), so the daemon is the sole writer of one file.
- One global sequence orders events across spaces; per-space files cannot do that without timestamps.
- Read verbs (`open_read`) open one fixed path instead of `<space>/ember.db`; mutating verbs already go through the socket, so they change nothing.

**Two bounds on the win**

- The gain is partial: answers, work dirs, traces, and session logs stay on disk per space. A UI reads the control plane — states, times, reasons, atoms, reports — from the one file, and walks the filesystem for content.
- The single DB requires N27 (a), the global hearth. N27 (b)'s per-space hearths are several writer processes and cannot share one file, so choosing the store decides the daemon.

**Recommendation (N28, rec a):** one DB, losses bought deliberately — a `spaces` registry table (id, path, paused); a space binding threaded through one query choke point, so filtering is architecture, not per-call discipline; `ember space export` for portability; content left on disk. The rejected alternatives: per-space files plus an `ATTACH`-based UI (works for few spaces, no global sequence, no one-file listing) and a daemon-written rollup metrics DB (a derived copy that drifts, the same fault that killed N23 (d)).
