## Goal

Understand what the warden's `coalesce` op buys, and check whether wisp already gives one wake per steer burst.

## Summary, one sentence

Wisp already wakes once for N queued steers, so no wisp change is needed; the warden's `coalesce` saves context, not runs, and the run-saving you want belongs in the hearth as a merge window.

## Summary, four sentences

`wisp steer` wakes nothing, and the next `wisp run` or `wisp continue` drains the whole inbox into one turn, so a burst costs one wake. Ember's `send` is not `steer`: `send` wakes on every message, and the hearth merges only what sits pending in one 250 ms tick. `coalesce` cannot merge runs that already started, and `design-options.md` §1 says exactly that, while G2 and G26 still imply coalescing bounds the run count. The fix sits in the hearth's `admit()` as a merge window (Q8), default 1500 ms, with `--andon` bypassing the window.

## The answer

### 1. Your premise holds: wisp costs one turn per burst

I verified this with the fake endpoint, no paid call. Three `wisp steer` calls, then one `wisp run`:

```
inbox lines before run: 3
POSTs: 1
steered user records: 3
request messages: [('user','Steering message added m'), ('user','Steering message added m'),
                   ('user','Steering message added m'), ('user','go\n')]
```

The code agrees:

| Where | What happens |
|---|---|
| `steer_command` (`wisp/wisp` 840-861) | appends one JSON line to `wisp.steer.inbox`; no liveness check, no wake |
| `steer_intake` (`wisp/wisp` 873-925) | renames the inbox, turns every line into one steered record, flushes once |
| `run_agent_loop` (`wisp/wisp` 802) | drains the inbox once, before the prompt |
| `loop_rounds` (`wisp/wisp` 1240) | drains at the top of every round, so all steers queued during one round land in the same request |

A steer never wakes anything in wisp. A steered record also never opens a segment and never resets the round counter. So N queued steers cost one wake and one turn, and N steers against a live run cost zero wakes and zero extra turns.

### 2. The wake in ember is `send`, not `steer`

| Layer | Who wakes | Batch width |
|---|---|---|
| wisp | nobody; the caller runs it | the whole inbox, one turn |
| hearth `deliver()` + `admit()` | the daemon | one tick, 250 ms |
| warden `coalesce` | nobody | a prompt one line long |

Q3 settled `send` as "always wake, except when the recipient is live". Therefore a burst spread over more than one tick against an idle member with a free slot costs one run per message. `admit()` starts a run on the first pending delivery; the second delivery arrives after the slot is taken, so the second delivery is soft or is held for a later wake.

### 3. Coalesce cannot fix those runs

`design-options.md` §1 line 160 says the hearth already merges the three deliveries into one run, so the warden does not save a run. The warden makes the merged question shorter. That is correct, and it is also the limit: `coalesce` runs after the wakes, so `coalesce` cannot undo a wake.

The design is inconsistent on exactly this point. G2 lists coalescing as a cost bound, and G26 says "coalescing merges messages", which reads as a run bound. Only held deliveries merge, and held means no slot or a parked model.

What `coalesce` still buys, with a merge window in place:

- one digest line instead of three excerpt blocks, so the prompt is shorter;
- one question instead of three, so the member answers once instead of three times;
- three fewer replies, and every reply would wake a peer.

That is a context and reply saving, not a run saving.

### 4. Do not change wisp; change the hearth

A steer that wakes would put a second writer on one session dir. That breaks the one-live-run law (G4) and the placement decision (S2). Keep the wake in the hearth.

The arithmetic fix is one constant. A delivery becomes eligible for `admit()` when the delivery is `EMBER_MERGE_WINDOW_MS` old, measured from the first pending delivery for that member. Then `deliver()` writes every body into the inbox, and one `continue` or `run` carries the whole burst. `--andon` skips the window. Soft deliveries and TTL are unchanged. The class table needs no new row: the delivery is `held` while the window is open, then `hard`.

Worked on the §1 example, at 1500 ms: the owner message at t+0 and the reply at t+2 share run one; the reply at t+4 and the "status?" at t+5 arrive while the run is live and are soft. Four wakes become one.

The cost is bounded latency: a lone message waits up to the window. That is why the value is a per-ember knob, and why `--andon` exists.

## The decision I need

Q8 asks for the default merge window. My recommendation is (b): `EMBER_MERGE_WINDOW_MS`, per ember, default 1500, `--andon` bypasses. Zero means today's behavior, so option (a) is a config value, not a separate build.

With Q8 answered, v0's "hard wake" gains one line: `admit()` skips a delivery younger than the window. The rest of v0 is unchanged.
