## Goal

Decide whether W0 `wisp send` survives for ember, answer your four challenges, and record the decision in the ticket set.

## TLDR

W0 is withdrawn: the prompt file, the `<!-- wisp:message -->` header, and `-F` had no job once the commands stay separate. The transport is `wisp steer --batch` (JSONL, one locked append, one key per body) plus `wisp run` / `wisp continue`; the ack is `wisp_steer_key`. A job never joins a live run; only a steer does.

## 1. Durability

You are right, and the fact is stronger than you stated. The steered record commits at the drain, before the first HTTP request, not after the first output. `steer_intake` appends the records and calls `flush_records` (`wisp/wisp:890-938`); `wisp run` drains before it reads its prompt (`run_agent_loop`, `wisp/wisp:803-827`).

So `wisp.jsonl` is the only durable record. `wisp.steer.inbox` is a transient mailbox: a line is either in the inbox or committed, never both. The old sentence made the prompt file a second queue and duplicated the log.

## 2. The header

Drop it. `<!-- wisp:message -->` existed only to delimit several messages inside one Markdown file. With no file, there is nothing to delimit. Stdin carries one message; `--key K` carries the ack. In a batch, the JSON field `"key"` carries it.

## 3. `-F FILE`

Drop it at the wisp level. W0's `<session>/wisp.prompt.md` was the command's target, not its source. `wisp run` and `wisp steer` already read stdin. Ember's own `-F` (a body file to the ember CLI) is a different surface and stays.

## 4. `--key`

Yes. `--key K` replaces the header for one message. A batch line carries `"key": "K"` instead. `steer_intake` writes the value as `wisp_steer_key` on the steered record and skips a key already committed in the epoch.

## 5. The map

| Situation | wisp command | Note |
|---|---|---|
| create a member | `wisp new` | no run, no tokens |
| job, member idle | `wisp run` | job body is the prompt |
| job, member live | hold; `wisp run` when the run ends | a job never joins a live run |
| steer, member live | `wisp steer --batch` | soft; no new turn |
| steer, member idle | `wisp steer --batch`, then `wisp run` | hard; one turn |
| digest + bodies, member idle | `wisp steer --batch`, then `wisp run` | `run` drains the inbox first; one turn |
| body, live, run ends before the boundary | ember re-checks at `reap()`, hard-wakes | one extra turn |
| steer, ember guesses live but the member is idle | the line waits; the next `wisp run` drains it | late delivery; Q22 |
| resume a killed segment | `wisp continue` | closed tail exits 78, then `wisp run` |
| distill | `wisp run` | no guard |
| fallback model | `wisp fork`, then `wisp run` | source session intact |
| ack | `wisp status --json` `committed_keys` | the JSONL stays the truth |

The hard wake is two commands, one turn:

```
{ printf '%s\n' "$DIGEST_JSON"; cat bodies.jsonl; } | wisp steer -d "$DIR" --batch
printf 'Continue with the messages above.\n' | wisp run -d "$DIR" --no-stream
```

`wisp run` drains the inbox before it appends the trigger, so the request order is digest, bodies, trigger. Each body line carries its key; the digest line carries none.

What you called `wisp steer --batch` and `wisp resume`:
- `--batch` is one atomic append of the digest plus N bodies under one lock. N separate `steer` calls can split the group across two round boundaries. `--batch` closes that.
- `resume` is dropped. `wisp continue` already resumes an open segment. A closed tail exits 78 under W4; ember then calls `wisp run`.

## 6. Why the merge looked useful

Ember did not know liveness at the transport call. The separated design answers that with three facts: `wisp status --json` reads the run lock, a wrong "idle" guess makes `wisp run` exit 76, and the steer lock makes a concurrent append safe. The merge saved one process and at most one tick. It saved no capability.

## 7. Is `wisp send` useful for ember after all

No. Its three pieces have smaller homes: W2 run lock, and W1 `wisp steer --batch` with the steer lock and the key. The only unique gain is "read liveness and start the run in one call," worth one process. A human joining a live session is the only real convenience case, and a shell function covers it. Ember does not need the verb.

## 8. Two questions this retraction forced open

- **Q24.** Your "I don't want 1 agent to run 2 jobs" changes Q3. A job to a live member is held; only a steer joins a live run. The surface for a steer is open: a distinct `ember steer <targets> -F FILE` verb (my recommendation), or a `--steer` flag on `send`/`dm`. I amended Q3 to the job/steer rule.
- **Q22.** The inbox has no expiry. An unread batch line can outlive its TTL, and a later run then delivers a stale message. Recommendation: stamp each line with `expires_at`, and let the intake skip an expired line.
