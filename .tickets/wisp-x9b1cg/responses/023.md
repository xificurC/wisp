**Goal.** Turn the owner's round-18 answer into the rule-language design: replace `--distill` with a prompt-bearing continuation, add a fork target, and put `--context-guard` and `--wallclock` on the rule.

**TLDR.** Three rule targets replace round 17's `--distill`. `--run TYPE` starts a fresh agent, `--resume` sends one more prompt into the stopped run's own wisp session, and `--fork` sends the prompt into a copy of that session. `--guard` and `--wallclock` become rule flags, and the prompt is the rule's `-F` body. No code changed.

**The continuation verb is `wisp run`, not `wisp continue`.** `wisp continue -d DIR` reads no stdin and appends no user prompt; that verb only finishes a segment a kill left open. The prompt-bearing continuation is `wisp run -d DIR`, which appends the prompt as a user record and drains a stale steer inbox. wispy's distill turn is exactly `wisp run -d <work session>` with no guard, so the engine copies wispy's shape without a new wisp verb.

**The surface.**
`ember rule add --event EXPR (--run TYPE | --run .parent | --resume | --fork) [-F BODY] ...`

- `--run TYPE` forks `agent-types/TYPE` into `runs/<rid>` with an empty work dir, as today.
- `--run .parent` keeps today's meaning: the type of the trigger run's parent.
- `--resume` creates a new run row over the trigger run's own session dir and work dir. The engine starts `wisp run -d <the same dir>` with the continuation prompt.
- `--fork` starts `wisp fork -d <source dir> -o runs/<rid>` and copies the source work dir. The engine then starts `wisp run -d runs/<rid>`. The source log stays frozen, and two forks of one run are two branches.
- `--resume` and `--fork` inherit the source run's type and persona, because the system record sits inside the copied log and W13 forbids rewriting records. A different persona needs `--run TYPE` plus file inputs.
- `BODY` is required for `--resume` and `--fork`, and `--run` refuses a body. `BODY` enters through `-F FILE` or `-F -` and is stored on the rule row.
- `--resume` and `--fork` need a conjunct that names a run, and `rule add` refuses a `started` conjunct. A `space.steer` trigger cannot carry either flag.
- A firing whose source run is not terminal fails `busy`, because one live run per session dir is a data-integrity law.

**The continuation prompt.** The engine writes a header with the rule, a `continues:` line naming the source run, its state, reason, and exit, the session dir, the work dir, the trigger atom, inputs, outputs, required fields, and the close line. The rule's body comes last, verbatim. The engine injects the contract, so a body never repeats a field name or an output path.

**Identity and tree.** N12 settles as a new run row whose parent is the source run. A green continuation answers the source run's fault atom and turns a failed tree green. A failed resume writes `agent-type:T.failed` again and retriggers its own rule, so a rescue rule carries a `--cap`.

**Results.** A resume shares the source's session dir, so both run rows would share one `results.jsonl`. A result row now names its run, and the engine reads only rows for the run it checks. A stale field from the source therefore cannot satisfy the continuation.

**Policy flags.** `--guard LIMIT` and `--wallclock S` are rule flags, stored on the rule and the run row, so a re-prompt inherits both. The engine passes `--guard` to wisp unchanged. Percent mode needs the model window in `wisp.modelcfg`, and wisp refreshes that file from `WISP_LLM_MODEL_INFO_FILE`, so `70%` works on a fresh fork. The guard must leave room for the continuation: the worker rule guards at 70 percent, and the resume rule carries no `--guard`, because a guard-stopped session sits at the limit.

**Naming.** The flag is `--resume`. `--continue` would collide with `wisp continue`, which means the no-prompt variant. `--resume` is the owner's own word.
