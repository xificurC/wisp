## The hearth

**There is no single global ember daemon.** One hearth tends one space: `ember hearth start` per space directory, socket at `<space>/hearth.sock`, one SQLite store per space. Spaces are isolation, not namespaces inside one daemon. The `ember` CLI is the stateless client half of the same program: mutating verbs go through the socket, reads open the database read-only.

The hearth exists because the chain **run → atom → rule → run** needs a process that is alive when a run exits, minutes after any CLI verb returned. Five jobs, all moments no CLI process witnesses:

1. **Fire rules on landed atoms.** `Hearth.pump` runs `evaluate_once` (unconsumed conjuncts), `apply_deferred` (steer joins), `admit`, `maybe_settle` — after every run finish and every mutating verb.
2. **Fill cap slots.** The cap is 3; a slot frees the instant a run exits. `admit` runs in the daemon; S2's wording: "nobody fills a slot that frees with no daemon."
3. **Watch children.** `Hearth.poll` reads exit codes, promotes a `starting` row to `live` when the run lock is held (the round-15 race fix), and turns exit 124 into `finish_failed(reason=wallclock)`.
4. **The steer join.** A steer firing inside the ~0.36 s spawn window appends to the live run instead of starting a duplicate; the join needs the watcher in that window.
5. **One writer.** All store mutations serialize through the daemon, so two CLI calls never race on SQLite.

The hearth holds no state beyond the store and child pids, so it is not a data risk: on start, `reconcile` crash-fails a non-terminal run whose lock is free and adopts one whose lock is held. A stopped hearth freezes the loop, not the runs. The alternatives lose: a CLI that re-pumps on every verb stalls when no human types; per-run wrappers chaining the next start are orphans with no cap arbitration; a wisp as coordinator was rejected in round 2 (the coordinator is arithmetic, a model there buys nothing). I added a "Why a hearth" section to `ember/README.md` carrying this.

## Human approval: three designs

Static only, per your framing; dynamic asking is deferred. All three share the same static shape you proposed: declared fields, a loop rule on the bool. Full text is `rule-language.md` §4.15; summary:

**A — the gate row (your idea, made real).** A rule takes `--require-human answer:string --require-human approved:bool` instead of a `--run` target; the firing opens a row in a new `gates` table holding the question (the rule body) and the field declaration. `ember gate list` shows open gates; `ember gate answer <gid> --field approved=true -F answer.md` type-checks and writes atoms `gate:<rule-id>.answer` and `gate:<rule-id>.approved=true`, so the loop rule is `--event gate:confirm.approved=false`. The cost: `tree_settled` and `tree_ok` read the `runs` table only, so a gate outside `runs` is invisible to closure — settlement, closure, and tree repair each grow a gate branch, and `--require-human` duplicates `--require` beside it.

**B — the human as a manual agent type (recommended).** The engine already has "a party that must return typed fields before its tree closes"; it is called a run. The target is `--run human:confirm` (a pseudo-type, no directory under `agent-types/`), and the rule keeps its existing flags: `--require answer:string --require approved:bool -F question.md`. The firing creates a run row with `mode manual` in state `waiting` — a member of `NONTERMINAL` and not of `LIVE_STATES`, so the two existing state lists give the waiting semantics for free: the gate blocks settlement and the root's `.done` closure exactly as a live run does, holds no concurrency slot, has no wallclock. `ember answer <rid> --field approved=true -F answer.md` completes it through the unmodified `finish_success`, so the atoms are `agent-type:confirm.approved=true` and the loop rule is the existing reviewer loop with a human in the reviewer's chair. Under N20 it becomes `ember agent add confirm --human ...`. Cost: one target spelling, one state, one verb, four guards (`admit` and `reconcile` skip manual rows — `reconcile` would otherwise crash-fail a dirless row, since a missing dir reads as a free lock; `answer_of` reads the stored answer text instead of `wisp.jsonl`).

**C — the atom-only gate.** `--gate NAME` writes a `gate:NAME.asked` atom and stops; `ember gate answer NAME --field ...` writes `gate:NAME.approved=true`. No row waits, so the space settles with the question open and closure fires before the human answers; the question-to-job pairing is the NAME alone, because events test subject, verb, and value, never fields. Honest only for a global, single-instance question ("may this space keep going" — Q31's hard-gate flavor), not per-job review.

**Recommendation: B.** The human differs from a worker on exactly one axis — the engine spawns nothing — and everything else (tree, closure, caps, atoms, the loop rule) is machinery that already runs.
