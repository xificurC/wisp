**Goal of this turn:** split the README recipe into the two loops the owner wants, answer whether rules should split into agents and rules, and record the design.

**TLDR:** Yes to the agent/rule split — it is the cleanest fix for the inheritance problem, and it is written up as §4.14 in `rule-language.md` with both recipes (N20, not yet code). Along the way I found a real defect in the current recipe's rescue cap: `handoff<3` never blocks a failing distill, because only a successful resume writes a handoff atom.

## WDYT: yes, split agents from rules

An agent row is a named run contract. `ember agent add NAME` carries `--type`, `--require`, `--in`, `--out`, `--guard`, `--wallclock`, `--model`, `--thinking`, `--trace`, and a body via `-F`. A rule row keeps only the wiring: `--event`, the target, `--cap`, `--id`. Reasons:

- The duplication is the disease. Today every `--run TYPE` rule re-declares the full contract, and every continuation rule re-declares it again by hand. Your continue example shows the cure: `--run agent:pickup --in session-file:handoff.md` inherits type, require, out, guard, wallclock, model — only the inputs differ.
- A rule-level `--in` **replaces** the agent's input list; nothing else is overridable. A different contract is a different agent. One way to say a thing.
- The body moves to the agent row, so `--resume agent:distill` takes its distill prompt from the agent. This answers your resource wish better than the round-17 store did: the prompt is named and versioned by its row. Round 18 settled N15 as "no resource store", and the settlement stands; `resource:` remains an output category only.
- On `--resume` and `--fork` the type comes from the source run, so a distiller agent omits `--type`.
- Bare `--run TYPE` stays as the anonymous one-off form, so existing rules keep their meaning. `.parent` stays for dynamic-type chains but leaves the recipes — I verified in `resolve_target`/`infer_parent` that `--run agent:pickup` on the handoff event produces the identical tree.
- Agent rows are immutable and versioned like cells; run rows pin the agent version, so failure reports reproduce their contract.
- N1 (type default fields) is subsumed: the agent row is the shared contract.

## Recipe A — the review loop

```
ember agent add pickup --type worker \
  --require ready:bool --in task:prompt \
  --out session-file:answer.md --guard 70% --wallclock 1800

ember agent add review --type reviewer \
  --require approved:bool --in task:prompt --in .out \
  --out session-file:review.md --wallclock 1800

ember rule add --event space.submitted --run agent:pickup
ember rule add --id review \
  --event 'agent-type:worker.ready or agent-type:worker.failed' \
  --run agent:review
ember rule add --id loop \
  --event 'agent-type:reviewer.approved=false' \
  --run agent:pickup --in task:prompt --in .out \
  --cap 'agent-type:reviewer.approved<4'
```

The disjunction ` or ` is new (N21); today two rules over the same agent do the same, since exactly one of ready/failed fires per worker run. The cap counts every approval atom (true or false): first review plus three restarts = four, so `<4` grants exactly three loops. On a failed worker, `.out` may hold a stale answer from an earlier loop round (`.` takes the latest cell version), so the reviewer persona branches on the trigger line and reads `ember query run:<id>`, which prints the full stored failure report — works today, no engine change.

## Recipe B — the distill loop

```
ember agent add pickup --type worker \
  --require ready:bool --in task:prompt \
  --out session-file:answer.md --guard 70% --wallclock 1800

ember agent add distill \
  --require handoff:bool --out session-file:handoff.md \
  -F distill.md

ember rule add --event space.submitted --run agent:pickup
ember rule add --id rescue --event agent-type:worker.failed \
  --resume agent:distill --cap 'agent-type:worker.failed<4'
ember rule add --id continue \
  --event 'agent-type:worker.handoff=true' \
  --run agent:pickup --in task:prompt --in session-file:handoff.md
```

Wallclock and guard both write `agent-type:worker.failed` with the reason as value; the bare event matches every reason (verified in `conjunct_matches`). The budget counts failures, not handoffs: each rescue firing needs a fresh failed atom and each cycle adds exactly one — the worker's stop, a continuation's stop, or a distill that itself fails (a resume inherits the worker type). The rule fires at counts 1, 2, 3 and blocks at 4: three cycles, whichever side fails. Any green worker heals the chain (every failed run has an answering resume child), the root turns green, and `agent-type:worker.done` fires; after three failed cycles the root stays red with `rule:rescue.capped`.

## The defect and the other corrections

- **`handoff<3` is wrong**: a failing distill writes no handoff, so the counter never moves and rescue fires unbounded. The README recipe now carries `failed<4`, and its "Limits" section states the hole.
- **No `ember resource add` exists by design**: round 18 settled N15 as (d), no resource store. The distill prompt was the rule's body; under the split it becomes the agent row's body.
- **The reviewer's `resource:review-latest.md` had no functional role**: the loop reads `.out`, pinned to the trigger run. The new recipes use `session-file:review.md`; `resource:` is for artifacts read by a fixed path later. (The test suite already used `session-file:` there — the README was the odd one out.)
