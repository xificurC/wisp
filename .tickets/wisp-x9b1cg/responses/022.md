**Goal:** Answer the two design questions: the meaning of `answer:`/`review:` in the recipe, and the proposed space `resource/` folder plus `--resume` rule target.

**TLDR:** `answer:` and `review:` are ad-hoc cell-name prefixes the README invented; the design defines only `task:`, `session-file:`, `steer:`, and `result:`, and the engine drops the prefix from the work-dir path. The resource proposal is sound; make a resource an immutable space file with a recorded hash, and make `--distill RESOURCE` a one-run target that forks the failed session, with a separate `--run .parent` rule for the fresh continuation.

## 1. `answer:` and `review:` are not design concepts

The design defines four cell categories (`rule-language.md` §4.2): `task:`, `session-file:`, `steer:`, `result:`.

The README recipe uses `answer:answer.md` and `review:review.md`. Those are legal only because `cell_ok` accepts any `CATEGORY:VALUE` (`ember/ember` 321-327). The category is part of the full cell name, not a namespace:

- `answer:answer.md` is a cell named `answer:answer.md`.
- `--out` injects only the value after the colon: `work/<rid>/answer.md` (`ember/ember` 786, 1264).
- The category is dropped from the filesystem path.

`answer:` and `review:` carry no semantic. The recipe uses them to make the two cell names distinct. `session-file:answer.md` and `session-file:review.md` are equally distinct. The README is wrong, not the design.

There is one real hazard: `answer:x.md` and `session-file:x.md` are two cells that resolve to one work file. The category is not a filesystem namespace, so a run can bind two cell versions from one file. Restrict `--out` to `session-file:` and reject the rest at `rule add`. That is N14.

## 2. The resource abstraction is right

Your authority argument holds. A rule that names `/home/.../distill.md` is not portable, not auditable, and points outside the space. A copied resource keeps the space self-contained.

Proposed shape:

- `<space>/resource/<name>` is the folder. `resource:<name>` is the rule-side reference.
- `ember resource add prompt/distill.md -F path/to/distill.md` copies the file in.
- The destination name is relative. `prompt/` is created if missing. Reject `..`, a leading `/`, and an absolute path.
- The source path never enters the rule. The rule stores the resource name and the hash seen at `rule add`.
- A duplicate add with different bytes is refused unless `--replace`. `--replace` names every rule that pinned the old hash.
- A firing hashes the file and compares. A mismatch fails with a named `resource_changed` report: rule, resource, expected hash, actual hash, fix command.
- `ember resource list`, `show`, and `rm`. `rm` refuses while a rule references the name.

Two corrections to your syntax:

1. Use `-F` for the source. R10f says a body arrives only through `-F FILE` or `-F -`. `ember resource add prompt/distill.md -F path/to/distill.md` is consistent. A positional source path is a small violation of the surface.
2. Drop the `/` root marker. A relative name with no prefix already roots at `<space>/resource/`. A leading `/` reads as an absolute path, and `cell_ok` rejects a leading `/` in cell values. `ember resource add distill.md -F ...` is the root form.

Caveat: the folder stops a rule from *naming* an outside path. It does not stop a run from *copying* an outside file in. Q38's flat authority records the creator and the hash; grants in v1 enforce the boundary. For v0, the record is the control.

Storage: a `resources` table plus the folder is enough for v0. Immutable names, one sha256, no versions. If you later need to replace a prompt in place, a `resource:` cell category is the upgrade path. That is N15.

## 3. `--resume` should be `--distill`, and one rule starts one run

The `wispy` shape is two steps:

1. A distill turn in the finished session, with no guard.
2. A fresh session seeded with the handoff.

One ember rule starts one run. Keep the two steps as two rows:

```bash
ember resource add prompt/distill.md -F wispy/prompts/distill-rules.md

ember rule add --id distill --event agent-type:worker.failed \
  --distill resource:prompt/distill.md \
  --require handoff:bool --out session-file:handoff.md

ember rule add --id restart --event agent-type:worker-distill.handoff=true \
  --run .parent --require ready:bool \
  --in task:prompt --in .out --out session-file:answer.md \
  --cap 'agent-type:worker.ready<4'
```

`--distill RESOURCE` means:

- Fork the *trigger run's session dir* into a new run dir.
- Append the resource text to the standard briefing.
- Run with no context guard.
- Parent is the trigger run.
- The rule declares the distill run's `--require` and `--out`.

`wisp fork` copies the whole conversation, so the distill turn sees the work. The failed run's log stays immutable. The fork takes the source run lock, so a live source exits 76.

Two design constraints:

- The distill run's type must differ from the failed type. Otherwise its own failure emits `agent-type:worker.failed` and retriggers the rescue rule. Use a derived label such as `worker-distill`. The type is a label only; no type dir exists. `prepare_run_dir` currently hardcodes `agent-types/<type>` (line 1166), so it needs an origin branch. This is verified by source read.
- The restart row's `--run .parent` resolves the worker type from the failed run and makes the distill run the parent. `tree_ok` on the failed run then sees the distill run, and `run_answered_fault` sees the `agent-type:worker.failed` trigger. The tree heals.

The name `--resume` collides with `wisp continue` and with the current `resume` row. `--distill` is the operation. Rename the second row `restart`. If you keep `--resume`, define it as "fork the failed session and run this prompt", and rename the second row anyway. That is N16.

## 4. The context half needs a guard

`spawn_run` passes `--wallclock` and no `--context-guard` (line 817-820). A context exhaustion therefore arrives as an endpoint error, exit 77, after the hard limit. The distill prompt adds tokens and may not fit.

The wallclock stop (124) is not a context stop. The `flow_exhaust` test works because the hanging run is short.

For the context half of the `wispy` shape, the worker run must be armed with a guard below the model's hard limit. The distill run must run without that guard. N11 asks where the guard value comes from; N17 asks how a rule arms it. My recommendation: a `--guard 70%` flag on the rule. Without it, `--distill` helps wallclock stops and short endpoint failures only.

## 5. What I would settle

- N14(a): `--out` is `session-file:` only.
- N15(a): a `resources` table plus `<space>/resource/`, immutable names, recorded sha256.
- N16(a): `--distill RESOURCE` as a one-run target, plus a separate `--run .parent` restart row.
- N17(a): a `--guard` rule flag, with the distill run explicitly unguarded.
- The README recipe changes `answer:` and `review:` to `session-file:` in the implementation round; the tests change with it.
