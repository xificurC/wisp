**One sentence:** billion-context is a proxy that lets the model fold mid-history ranges into ref-addressable summary blocks as work proceeds, where wispy instead summarizes a whole wisp session at a boundary and restarts.

**Four sentences:** billion-context intercepts the request body between the agent CLI and the model API and keeps a "fold" in the conversation: a digest prefix of tiered summary blocks plus a raw recent zone. The model decides when, what, and how much to compress; a pure TypeScript kernel does the bookkeeping and enforces protected zones. ## What billion-context is

A TypeScript project (MIT, npm package `billion-context`, binary `bili`) that sits between an agent CLI and a model API. It works three ways: as an in-process plugin in a host, as a launcher that starts a proxy, or as a `/bili/` base-URL rewrite. All three end at the same place — `bili` rewrites the request body.

The interesting piece is `kernel/`, a pure TypeScript library with no I/O and no model calls. `kernel/DESIGN.md` states the split plainly: the model writes the summary text, and the kernel orchestrates everything else.

The paper (`paper/model-driven-incremental-hierarchical-compression-*.md`, preprint v0.2) reports 4.5 months of daily production use, 174,327 calls, 18.76B cumulative input tokens across hosts, zero window violations on 204,800-token models, and 31–54% fewer billed tokens against a retention baseline. The evidence markers in the paper separate verified production numbers from simulation. Expect marketing gloss around a real mechanism.

## How the fold works

**Layout.** The visible window holds a prefix of digest blocks plus a raw recent zone (tens of K tokens). A kernel floor protects the last few messages, the last user message, and the first user message. The lecture-call records themselves are hidden after use, so the compression scaffold leaves no trace.

**Refs and blocks.** Every message gets a stable ref (`m00420`). The model calls `compress` with `{startRef, endRef, summary, topic}`. The kernel allocates a `CompressionBlock` with tier, topic, summary, `directMessageIds`, and transitive `effectiveMessageIds`. The range deactivates; nothing is deleted. `decompress` puts a block's sources back into context; `decompress-to-file` writes full text to disk and leaves the prefix untouched; `search_context` greps block summaries.

**Tiering.** Tier-2 folds tier-1 blocks into new blocks that point at their sources; tier-3 folds tier-2. The paper calls the shape a pagoda, and the design is an LSM tree over prose. Each piece folds once and then resides unchanged, so retention stops at about 1/8 instead of decaying geometrically. Production tier-2 usage is rare (60 of 1,711 blocks), so tiering is a safety valve, not a routing path.

**Trigger.** The kernel injects a nudge when the context is above 45% of the window **and** has grown past a floor since the last compression (default 50K, effective 22.5K). The nudge lists candidate ranges with real token sizes and tool/text share. The nudge never prints a fill percentage, and it is phrased as an efficiency hint with the right to refuse. Production logs show 22% of compressions happen on turns with no nudge at all.

**Why append-only matters.** Compression only deactivates a mid-history suffix range, so the established prefix never invalidates. The paper measures a 94.2% cache-read share at active tempo.

## Comparison with wispy

| axis | wispy today | billion-context |
|---|---|---|
| unit | whole wisp session, at a boundary | mid-history range, many small folds |
| trigger | 70% guard, hard stop (exit 75) | fill **and** growth gate, model may refuse |
| who writes | model writes ticket and STATE.md, one unguarded turn | model writes the summary, kernel keeps the books |
| durability | ticket (merged record) + STATE.md (handoff) | blocks with lineage, append-only state |
| restore | source sits in `wisp.jsonl`, reachable by path only | per block, by ref, via tool |
| enforcement | `check_state` prints notes, never fixes | kernel enforces floors, prompt only requests |

**Measured on this repo's three live tickets** (session `wisp.jsonl` plus recorded usage, 2026-11-09):

- Standing fold — bytes of all session jsonl against ticket plus STATE: `ai-wpueub` 65×, `wisp-5rva5v` 126×, `wisp-o2llma` 89×. wispy's compression ratio sits in the same order as billion-context's reported 70×.
- Session mass — tool results 35–44%, reasoning 26–31%, tool-call arguments 7–21%, user prompts 6–16%, system 7%, assistant text 2–3%.
- Billed input — 3.25M tokens over 70 rounds, 14.1M over 259, 22.4M over 409. Peak context 78K / 125K / 160K. Resend amplification (cumulative prompt divided by final context) is 42×, 113×, 140×.

Three differences follow from those numbers. wispy's retention is genuinely good, because the ticket merges rather than re-summarizes. wispy pays for the fold at resend time instead, because each round resends the whole history. And reasoning is the second-largest mass in a wispy session, while billion-context never folds reasoning (it drops reasoning from compress calls).

The recorded usage carries no cache fields at all, so wispy cannot see its own cache-read share today.

## What could be ported, cheapest first

1. **The doctrine, as text.** Add billion-context's KEEP VERBATIM / DROP / PRIORITY classes and its "TASK AS OF THIS BLOCK" labelling to `wispy/prompts/distill-rules.md`. No code. Highest value per line: wispy's rules say where a fact goes, and say nothing about which facts survive.
2. **Sizes in the distill prompt.** About 40 lines in wispy: read `wisp.jsonl`, print per-round token totals, tool versus text share, and user-message anchors. The distill turn currently decides with no inventory.
3. **Band plus growth gate.** About 60 lines: fire the distill at 45%+ and after a growth floor, drop the percentage from the text, and accept a "NOT YET" reply that returns to the same session (`wispy continue` already exists).
4. **An enforcement floor.** `check_state` notes problems and never fixes them. Gate instead: a Cache line must name an existing source, an open objective must appear in the ticket or the STATE `Open`, and the cap becomes a cut.
5. **Refs in wisp.** Number the records, add `wisp slice -d DIR -n 12:40`, and require Cache lines to cite a ref. About 60 lines. Makes restore real and cheap.
6. **The mid-session fold.** The real port, 250–400 lines in wisp. A `fold` record type covers a record range at render time, so `wisp.jsonl` stays append-only and the fold is a projection. The guard fires a fold instead of a stop. Pays the 42–140× resend amplification; costs wisp its three-tool simplicity.
7. **A cache ledger.** About 20 lines: record cache fields when a provider reports them and warn when the share collapses.
8. **Tier-2 over `states/`.** Only after wispy grows a tier-1 fold. Low priority.

Not portable: proxy and MITM plumbing, host adapters, plugin installers, billing, image rescale, output steering, and the 2,600-line configuration surface.
