## TLDR

Yes. The amend is the operator repair path: the commit session writes the name and derives the subject from that name; wispy checks both after the commit and, on a failure, exits 1 and leaves the commit in place; the fix is a name edit plus `git commit --amend`. `wispy` itself never runs an amend.

## The sequence

`cmd_commit` runs three post-commit checks on the committed state, in this order (`wispy/wispy`):

1. `wispy/wispy:1182` — `name_problem(meta.get("name", ""))` reads the frontmatter of `ticket.md` as it sits in the commit, not the session's answer. The model can say it renamed the ticket without renaming it. A question name, an auxiliary lead word, or more than 12 words yields a note on stderr: `repair: write the name in <ticket.md path>, then amend the commit`, and exit 1.
2. `wispy/wispy:1188` — `expected = commit_subject(named)` builds `<status>(<id>): <name>` from the committed frontmatter status, id, and name (`wispy/wispy:558`). wispy compares `expected` with `git log -1 --format=%s`. A mismatch prints both strings and the same repair line, then exits 1.

Both failures come after the session already committed, so the bad commit is already HEAD. `wispy` never resets, rebases, or amends anything: the only occurrences of "amend" in `wispy/wispy` are those two note strings.

## Why an amend and not a second commit

The subject lives in the commit object and does not follow later edits to `ticket.md`. Fixing the `name:` line alone leaves the frozen subject disagreeing with the record the next `name_problem` call and the next subject comparison read. `git commit --amend` rewrites that same commit object, so the log never carries a bad-subject commit followed by a "fix subject" commit.

The full repair: edit `name:` in `ticket.md`; stage the ticket dir, since the record is part of the commit; rebuild the subject from the committed status and id (`closed` after `--close`, otherwise `wip`) and the new name; run `git commit --amend`. Do not push.

Two side facts about the repair path:

- `wispy` does not re-run the gates on a retry. A rerun of `wispy commit` with a clean work tree prints `work tree clean; nothing to commit` and returns 0 before any session or check starts. The manual amend is therefore verified by the operator, not by wispy.
- A correction needs judgment about the work, and the ticket's Out of Scope forbids a second model call or a separate naming session. That is why the tool reports and stops instead of rewriting the commit itself.

## The other amend, unrelated to failure

`wispy/prompts/commit-rules.md:99` carries the session-side rule: the commit session makes exactly one new commit and does not amend, unless the user asked for an amend through the request or a `<steering>` block. That path covers history shaped before the session started. The repair amend above covers a name the session wrote badly.
