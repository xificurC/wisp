## Core shape

Three layers, deliberately separated:

1. **Board** — a filesystem protocol. It holds tasks, claims, leases, results, and verdicts. It applies deterministic reflexes only: atomic claim, lease expiry, race expansion, sibling completion.
2. **Pools** — actuators per role. A pool claims a ready task and runs one `wisp` session. It holds no plan.
3. **Router** — a black-box command that returns `(model, thinking, guard)` for a work class and the current load snapshot.

Any worker can split. Any verifier can add repair tasks. Any designer can add child tasks. No agent owns the global plan.

## Options

| Axis | Options | Recommendation |
|---|---|---|
| Substrate | tikit/wispy per task; `.swarm/` file-per-task board; SQLite board | File-per-task board. tikit stays the human record. |
| Activation | role pools; recursive spawning; hybrid | Hybrid: seeded design task, then role pools. |
| Agent lifetime | one session per attempt; long steering session | One session per attempt. |
| Evolution | race + judge; hill climb; tournament; island | Race + judge, 3 candidates by default. |
| Router | static table; load-aware score; bandit; external service | Load-aware score behind the `route` hook. |

The recommended combination is **B + hybrid pools + one session per attempt + race/judge + load-aware router**.

## Evidence from LiteLLM

The company proxy exposes enough for the optimizer, with the existing key:

- `/health` (~6 kB): healthy endpoints plus Azure remaining request and token quotas.
- `/v1/model/info` (~254 kB): prices, context windows, reasoning and tool support.
- `/metrics/` (~12.8 MB): global in-flight, per-deployment requests, failures, latency, TTFT, queue time, rpm/tpm limits.
- No per-model in-flight gauge. Sample cumulative counters twice and diff.
- A 3 s sample showed about 80 global in-flight requests and 40 rpm on `DeepSeek V4.1 Flash`.

The metrics payload is too large for per-agent fetching. The design uses one sampler every 15 s writing `router/snapshot.json`. The router falls back to a static table when the snapshot is stale.

## Wisp facts that shaped it

- `wisp new` fixes model and system prompt, so routing is a session-creation decision.
- Wisp has no temperature. Candidate diversity must come from approach seeds, model choice, or context packs.
- Wisp has no API retry. The pool owns retry and fallback.
- `wisp.jsonl` mtime is a free heartbeat because wisp commits every finished round.
- Wispy distills every work session. That is too expensive for leaf tasks, so leaves use a `result.md` contract instead.

## Open decisions

The ticket lists them as G1–G7. The important ones:

1. Accept the new `.swarm/` tree, or keep everything as tikit tickets?
2. One repository, one ticket, or many?
3. Is a pool process acceptable under “no top-level orchestrator”? It starts work but holds no plan.
4. Commit per task or per race?
5. Always 3 candidates, or only where more than one solution can pass?
6. Does any class need a human gate before merge?
7. What concurrency is safe for the shared proxy? Start at 8.

If you accept the shape, the first implementation slice is the board protocol plus the three personas, with no evolution and no router. That proves the loop before adding races.
